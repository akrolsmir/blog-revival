# 2026-07-23 — Merged the two demo skins into one route tree, selected by dark/light mode

This describes the code as of 2026-07-23. If it disagrees with the current
code or CLAUDE.md, trust those.

## What & why

The site originally shipped as two parallel demo frontends with identical
features: a dark cemetery skin at `/graveyard/**` and a 2005-WordPress
pastiche at `/wordpress/**`, with a chooser page at `/`. That made every
shared link skin-specific and every page exist at two URLs.

Now there is one route tree, and the skin is picked by the visitor's
dark/light mode preference:

- **dark mode → graveyard** (`gy`)
- **light mode → WordPress** (`wp`)

The theme follows the OS setting until the visitor explicitly toggles (the
floating ☀/🌙 button, bottom-right corner in both skins); an explicit choice
persists in localStorage. The URL no longer encodes the skin, so a shared
link opens in the recipient's preferred mode.

## What changed

- `app/graveyard/**` and `app/wordpress/**` page bodies moved (as git
  renames) to `components/<skin>/pages/*`; the per-skin layouts became
  `components/<skin>/Shell.tsx`. New thin routes in `app/(site)/`.
- All ~50 skin-prefixed links (`/graveyard/...`, `/wordpress/...`) became
  root-relative, including `signin?next=` params.
- The `skin` request parameter was dropped from `/api/checkout` and
  `/api/connect/onboard`; Stripe return URLs no longer include a skin
  prefix.
- The old chooser at `/` moved to `/choose`; `/graveyard/*` and
  `/wordpress/*` became force-theme redirects.
- Added `next-themes`, `lib/theme.tsx`, `components/ThemeFab.tsx`, and the
  `html.skin-*` background rules in `app/globals.css`.

## How it works

- **`lib/theme.tsx`** wraps [next-themes]. The provider maps
  `dark → skin-gy` / `light → skin-wp` classes on `<html>`, set by an inline
  script before first paint, so the background color (see `html.skin-*`
  rules in `app/globals.css`) is correct before hydration and there is no
  flash of the wrong skin.
- **`useSkin()`** returns `"gy" | "wp"`, or `undefined` until after mount.
  The server prerenders with no knowledge of the theme, so skinned trees
  must not render during hydration; every consumer returns `null` while it
  is `undefined`. The resulting blank period shows the correct background
  and looks the same as the InstantDB live-query loading states all pages
  already have.
- **Routes** live in `app/(site)/`: `/`, `b/[slug]`, `p/[handle]`,
  `patrons`, `signin`, `account`, `claim`. Each `page.tsx` is a thin client
  switch: `skin === "gy" ? <GyX/> : <WpX/>`. The `(site)/layout.tsx` does
  the same for the chrome, wrapping children in `GyShell` or `WpShell`, and
  renders the `ThemeFab` switcher once, outside both shells.
- **Per-skin code** lives entirely under `components/graveyard/**` and
  `components/wordpress/**`: page bodies in `pages/*`, chrome in
  `Shell.tsx`. Shared logic stays in `lib/`; only markup differs. When
  adding a feature, keep the two skins feature-equivalent. Each route
  imports both variants, so a missing one shows up quickly.
- **Legacy URLs**: `app/graveyard/[[...rest]]` and
  `app/wordpress/[[...rest]]` catch old skin-prefixed links, force the
  matching theme, and redirect to the unified path
  (`/graveyard/b/foo` → `/b/foo` in dark mode). `/choose` keeps the old
  side-by-side demo picker; its two links go through these redirects.

## Gotchas

- **Never put `.gy`/`.wp` on `<html>`.** Those classes carry typography —
  `.wp` sets a 13px base font-size, which on the root element would rescale
  every rem unit site-wide. The html-level `skin-*` classes set only the
  background; the full skin classes stay on the shells' wrapper divs.
- **Don't render skinned trees before mount.** Anything branching on skin
  must go through `useSkin()` and tolerate `undefined`; branching on
  next-themes' `resolvedTheme` directly during render causes hydration
  mismatches.
- **Don't write skin-prefixed URLs.** No `/graveyard/...` or
  `/wordpress/...` links in components, and none in Stripe return URLs
  (checkout, Connect onboarding) — the old `skin` request parameter was
  removed.
- Root layout's `<html>` needs `suppressHydrationWarning` (next-themes
  mutates its class before React hydrates). Keep it.
